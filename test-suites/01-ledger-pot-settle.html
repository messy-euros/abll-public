Ledger TDD Suite

Night at the Races — Architecture A. Tests written against a contract, run first against an empty stub. They should all be red for the right reasons before any real code exists. Then swap in an implementation and watch the same suite go green — or not, and fix.

The loop this page runs

1 · Stub — no behaviour implemented. Every test fails with NotImplemented. That's the good red: the test fails because the feature is absent, not because the test is broken. If any test went green against the stub, that test would be worthless.
2 · Correct impl — the same suite, unchanged, run against a real ledger. All green.
3 · Correct − one seeded bug — idempotency removed from top-ups. The suite pinpoints exactly one red (duplicate webhook) while everything else stays green. That's the regression catch you're building this for.

The contract under test

This is the interface the eventual backend must satisfy. Green means the implementation honours it; the tests never change between stub and real code.

balance(player)            -> integer cents
topup(player, cents, source, ref?)   -> {ok, reason?}   // idempotent on ref
openRace(id, lockTs)  /  lockRace(id)
placeBet(player, raceId, horse, cents, nowTs) -> {ok, reason?}
      // rejects if: race not open, nowTs > lockTs, amount invalid, balance < amount
settle(raceId, winningHorse) -> {ok, pot, houseCut, payouts:[{player,cents}]}
      // pot == Σpayouts + houseCut, exactly, incl. rounding
exportLog()  ->  array          // append-only; balances are Σ of it
recover(log) ->  ledger         // rebuild identical balances after a crash
